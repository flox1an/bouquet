Do we need a client-side graph database?

Decision point: relationship model, not storage product. Bouquet already has React Query + Nostr event cache + server blob list.

A. Typed in-memory graph index

Build a normalized object graph from blobs + Nostr events + parsed playlists. No dependency.

Graphology / Cytoscape-like model
nodes + edges + algorithms

B. Browser graph library

Useful if we need traversal algorithms, visualization, centrality, graph queries.

Client graph DB / persisted query layer
extra schema + storage + sync

C. Client-side graph database

Possible in JS, but likely overkill unless offline persistence and arbitrary graph queries are product requirements.

Recommendation: A. Keep graph as derived state. Persist only existing source facts (blobs/events); rebuild relationships cheaply. Add a graph library later only if UI needs real graph algorithms.
